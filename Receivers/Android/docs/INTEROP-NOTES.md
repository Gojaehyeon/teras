# Android receiver — interop notes

The authoritative interop vectors live at `docs/VECTORS.md` in the repository
root and are generated by the Swift reference implementation. This receiver does
not publish its own copy; `InteropVectorsTest` parses that file and asserts the
Kotlin implementation reproduces every value in it, so the Swift side stays the
single origin.

Run it with:

```sh
./gradlew testDebugUnitTest --tests '*InteropVectorsTest'
```

The underlying primitives are separately checked against published vectors
(FIPS 180-2 for SHA-256, RFC 4231 for HMAC-SHA256, RFC 5869 for HKDF, the GCM
specification's test cases 13 and 14 for AES-256-GCM) in `CryptoPrimitivesTest`,
so a passing interop test means agreement with the standards and not merely with
the other implementation.

Field encodings this receiver relies on, all as confirmed by the reference:
`hostNonce`, `deviceNonce`, `proof` and `box` are standard Base64 strings in the
JSON; the HKDF salt is `hostNonce ‖ deviceNonce` (32 bytes, host first); the
pair-box nonce is 12 zero bytes; the ENC nonce is 4 zero bytes followed by the
u64 big-endian counter; and the ENC additional authenticated data is the single
byte `0x7F`.

## Readings taken where PROTOCOL.md is ambiguous

There are no deviations from the specification. These are the choices made
where two readings were possible; each is what a Swift implementer working from
the same document would most plausibly write.

### 1. POINTER button for a right click — the one genuine conflict

§6.1 says a long press "sends POINTER with button=2", but the §6.4 field
layout defines `button 0 left 1 right 2 middle`. **This receiver sends
`button = 1` for a right click**, because §6.4 is the normative encoding of the
field and §6.1's parenthetical would otherwise emit a middle click. A host that
switches on §6.4's table interoperates with this receiver unchanged. If the Mac
side instead implements §6.1 literally, fix §6.1 rather than either
implementation.

### 2. Identifier spelling inside `pinKey`

`deviceId` and `hostId` are hashed as the exact UTF‑8 bytes of the strings that
travelled in HELLO and HELLO_ACK. No case folding and no brace or hyphen
normalisation. Swift's `UUID.uuidString` is upper case while this receiver's
`java.util.UUID.toString()` is lower case, so each side must hash the string it
*received*, not a re‑rendered one. The vectors above use the lower‑case
spellings given.

### 3. `authRequired` is not taken purely from `hello.transport`

§3.2 says `authRequired` is "true on lan, false on usb". A receiver cannot
verify a transport claim, and an Android USB session always arrives through
`adb forward` on 127.0.0.1. This receiver therefore reports
`authRequired = false` only when the host claims `usb` **and** the peer address
is loopback. Anything arriving from the LAN must pair, whatever it claims.

### 4. Recovery when the host lost its secret

§3.3 keeps the stored secret on AUTH_FAIL, so a host that lost its own copy
would see `paired = true` and have no way forward. This receiver accepts a PAIR
frame while waiting for AUTH: it treats it as a re‑pair request, shows a fresh
PIN and answers PAIR_REQUIRED. The stored secret is still never discarded on an
unauthenticated peer's say‑so. Users can also clear every secret from the
receiver's settings screen.

### 5. `pv` in HELLO_ACK

Reported as `min(1, hello.pv)` per §9, rather than echoing the host's value.

### 6. SCROLL units and sign

`dx`/`dy` are the finger or wheel movement in points (pixels divided by the
display density), not the content movement. Positive `dy` means the fingers
moved **down** the screen and positive `dx` means they moved right. A wheel
notch is reported as 16 points. The host decides whether to invert for natural
scrolling.

A two‑finger gesture emits `SCROLL` phase 0 on the second finger landing, phase
1 per movement batch, and phase 2 when a finger lifts. The single‑finger TOUCH
that preceded it is cancelled (phase 3) so the host does not leave a button
pressed.

### 7. Stylus tilt fields

§6.1 carries `tiltX`, `tiltY` and `azimuth`, which is one value more than a
stylus reports. Android gives a single tilt off the panel normal plus an
orientation. This receiver sends, all in radians:

```
tiltX   =  tilt * sin(orientation)
tiltY   = -tilt * cos(orientation)
azimuth =  orientation                (Android AXIS_ORIENTATION)
```

so `azimuth` and the `(tiltX, tiltY)` pair carry the same information in the two
shapes a host might want. `pressure` is clamped to `[0,1]`. Finger touches send
zero for all three angles.

### 8. VIDEO presentation timestamps

`captureTimestampUs` is on the *host's* monotonic clock. It is not used as the
MediaCodec presentation timestamp; the receiver supplies its own monotonic
values and keeps the capture stamp alongside, converting it with the clock
offset derived from PING/PONG to report `e2eMsP50`.

### 9. PONG `t_recv_us`

Filled with the receiver's own monotonic microseconds at the moment the PING was
processed. Combined with the round trip it yields
`offset = t_recv - (t_echo + rtt/2)`, which is what turns `captureTimestampUs`
into a glass‑to‑glass figure. No wall‑clock epoch is implied.

### 10. STATS precision

Every floating‑point field is rounded to one decimal place before being sent, so
the JSON stays compact at one frame per second.

### 11. `screen` is the whole panel

The receiver runs edge to edge behind the system bars while streaming, so the
*usable* full‑screen size in §3.2 is the full panel in physical pixels
(`WindowMetrics.getBounds()` on API 30+, `getRealMetrics` below that). Only a
display cutout removes usable pixels, and that is what `safeInsets` reports.
`scale` is the display density and `refreshHz` the current mode's refresh rate.

### 12. `orientation` on natural‑landscape tablets

Decided from the reported bounds first and the rotation second: a device whose
natural orientation is landscape reports rotation 0 while showing a landscape
picture. Landscape with rotation 270 is `landscapeRight`, any other landscape is
`landscapeLeft`; portrait with rotation 180 is `portraitUpsideDown`, otherwise
`portrait`.

### 13. Triple tap

The stats overlay toggle is a plain triple tap on the picture, and those taps
are still forwarded to the host as ordinary clicks. Suppressing them would delay
every single tap by the triple‑tap window, which costs far more than three
stray clicks.
